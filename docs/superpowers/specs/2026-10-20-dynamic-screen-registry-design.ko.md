# 화면 목록을 실행 중에 바꾸기 — 설계 제안

[English](2026-10-20-dynamic-screen-registry-design.md) · **한국어**

- 날짜: 2026-10-20
- 상태: **소유자가 A안을 골랐다(2026-10-20).** 구현은 별도 계획으로 이어진다.
- 패키지: `@devslab/workspace` 0.2.0 (main `08ae79a`)
- 첫 소비처로 생각하는 곳: fm-dental (`src/features/admin/workspace/`)

## 1. 왜 필요한가

지금 패키지는 워크스페이스를 만들 때 화면 전체 목록을 받아야 하고, 그 목록은 이후 바뀌지 않는다. fm-dental은 화면을 미리 알 수 없다. 라우터가 사용자 권한을 확인하고 데이터를 불러온 다음에야 그 화면이 생긴다. 그래서 fm은 패키지가 생기기 일주일 전(fm PR #67, 2026-10-01)에 자체 탭 모델을 만들었고, fm PR #126에서 패키지를 들일 때도 `RetainedPanels`만 가져오고 탭 모델은 그대로 두었다.

그 대가가 2026-10-20에 드러났다. "다음 화면을 기다리지 않고 탭 닫기" 수정을 두 번 써야 했다. 패키지에 한 번(devslab-kr/workspace#7, 0.2.0), fm에 한 번(fm PR #151). 소유자는 패키지가 화면 목록을 실행 중에 받을 수 있게 하자는 데 동의했다. 그러면 fm은 나중에 탭 규칙을 패키지에 넘기고, 진짜 fm 몫인 라우터·권한·업무 데이터만 남길 수 있다.

**목표:** 실행 중에 화면을 추가·수정·제거할 수 있고, Solid·React·Vue·Svelte에서 똑같이 동작해서 fm이 탭 모델을 패키지로 옮길 수 있는 상태.

**범위 밖:** 라우터, 권한 확인, 데이터 캐시, fm의 화면 디자인. 패키지는 여전히 네트워크를 부르지 않는다.

**동작은 해도 실패로 보는 경우:** 목록이 바뀌었다고 보관 중인 페이지가 입력값을 잃는 것, 권한이 회수된 화면이 계속 보이는 것, 0.2.0 닫기 규칙이 조용히 바뀌는 것, fm이 손으로 맞춰야 하는 두 번째 상태 기계가 남는 것.

## 2. fm에 필요한 것과 패키지가 주는 것

| fm에 필요한 것 | fm이 지금 하는 방법 | 패키지 0.2.0 | 빈 곳 |
| --- | --- | --- | --- |
| **라우터가 성공한 뒤에만 화면 등록.** 화면(컴포넌트와 로더 데이터)은 `beforeLoad`와 로더를 통과해야 생긴다. | `WorkspaceRoute`가 라우터 성공 뒤 route 렌더에서 `register()`를 부른다(`AdminWorkspaceRoute.tsx:33-50`, 서버에서는 동기로 등록 `:45`). | 목록은 `createWorkspace({ screens })`에서 고정된다(`core.ts:17`). 목록에 없는 id를 `open()`하면 가드를 부르기 전에 `unknown`(`core.ts:37`). | 실행 중에 화면을 추가할 방법이 없다. |

| **보관 탭은 먼저 보여 주고 나중에 확인.** 열린 탭을 누르면 라우터가 뒤에서 다시 확인하는 동안 화면을 바로 보여 준다. | 이동 전에 활성 경로부터 바꾼다(`AdminWorkspace.tsx:229-238`). | `open()`은 `beforeActivate`가 끝난 뒤에만 반영한다(`core.ts:40-53`). 이웃을 먼저 보여 주는 건 0.2.0 닫기뿐이다. | `open()`에 "보관 탭 먼저 보여 주기"가 없다. |

| **대기 중 표시.** 라우터가 새 화면을 아직 확인하는 동안에도 탭 줄에 메뉴 제목을 단 자리표시 탭이 바쁨 표시와 함께 보인다. | `readChromeTabs()`가 겉모습용 탭을 더한다(`AdminWorkspace.tsx:107-118`). | 없음. 스냅샷에 대기 상태가 없다. | 그릴 근거가 될 대기 상태가 없다. |
| **비지 않기.** 마지막 탭을 닫으면 그 영역의 홈 화면으로 가고, 홈 탭만 남았으면 닫을 수 없다. | `close()`가 `home()`으로 돌아가고 닫기 버튼을 끈다(`AdminWorkspace.tsx:273-275`, `:375`). | 마지막 탭을 닫으면 빈 상태. | "홈" 규칙이 없다. |
| **SSR.** 서버가 방문한 페이지를 그 탭과 함께 그린다. | 서버 렌더 중에 route가 탭 줄보다 먼저 등록하고, 탭 줄은 서버에서 늦게 읽는다(`AdminWorkspace.tsx:116-118`). | "SSR 전에 요청별 컨트롤러로 미리 열어 두라"(README). 고정 목록일 때만 해당. | 등록된 화면에 대한 네 어댑터 공통 규칙이 필요하다. |

반대로 패키지가 **가져가면 안 되는** fm 것도 있다. 라우터 연결 자체, 권한·메뉴 모델, `warmPageCode`, 선택값 넘기기, Realtime/Usage/Guide provider, 오류 경계, DOM을 복제하는 전환기 미리보기, DDS 기반 화면 디자인.

## 3. 어떤 안이든 지켜야 할 규칙

1. **0.2.0 닫기 계약은 출시된 그대로.** 활성 탭을 닫으면 바로 없어지고 이웃이 보이며, 그다음 이웃을 `beforeActivate`로 확인한다. 거절되면 `denied`이고 활성 화면이 없다. 다른 요청에 밀리면 `stale`(CHANGELOG 0.2.0).
2. **코어는 프레임워크와 무관하게**: DOM, 네트워크, 타이머, 라우터, 저장소 없음(`core.ts:1`). 라우터 연결은 앱이 주는 가드에 둔다.
3. **목록이 바뀌었다고 보관 페이지를 다시 만들지 않는다.** 제거(닫기, 회수, 초기화)나 명시적인 교체만 페이지를 버린다.
4. **Solid·React·Vue·Svelte가 똑같이 동작한다.** 규칙마다 코어 테스트와 어댑터 동등성 검사를 둔다.
5. **버전:** 패키지는 0.x라서 마이너(0.3.0)가 깨질 수 있다. 깨지는 것은 모두 CHANGELOG의 **Breaking**에 적는다.

## 4. 안

### A안 — 컨트롤러 안의 살아 있는 목록 (앱이 넣어 줌)

컨트롤러가 목록을 계속 갖되, 바뀔 수 있게 한다. 앱은 라우터가 성공하면 화면을 넣고, 권한을 잃으면 뺀다.

```ts
interface Tab<D = undefined> { id: string; slot: number; instance: number; data: D }
interface Snapshot<S, D> {
  tabs: readonly Tab<D>[];
  screens: readonly S[];       // 현재 목록. 바뀔 때마다 새로 만든다
  activeId?: string;
  pendingId?: string;          // 확인(beforeActivate)이 진행 중인 id
  switcherOpen: boolean;
}
interface Options<S extends Screen, D> {
  screens?: readonly S[];                      // 시작 목록 (예전엔 필수)
  createTabData?: (screen: S) => D;            // 새 탭 인스턴스마다 한 번 호출
  showRetainedFirst?: boolean;                 // 기본 false
  home?: string | (() => string | undefined);  // 워크스페이스가 비지 않게 하는 화면
  maxTabs?: number; beforeActivate?; beforeClose?; onChange?;   // 그대로
}
// 새 컨트롤러 메서드 (open/select/close/showSwitcher/... 시그니처는 그대로)
register(screen: S, options?: { show?: boolean; renew?: boolean }): Result; // 'ok' | 'limit'
unregister(id: string): boolean;
retainOnly(ids: Iterable<string>): readonly string[];   // 제거된 id 목록을 돌려줌
show(id: string): Result;                                // 'ok' | 'unknown' | 'limit', 가드 없음
getScreen(id: string): S | undefined;
getTab(id: string): Tab<D> | undefined;
canClose(id: string): boolean;
```

**동작을 쉬운 말로.** 아래에서 "확인"은 컨트롤러가 부르는 모든 `beforeActivate`를 말한다. `open()`/`select()`, 닫힌 탭의 이웃(0.2.0), 홈, 먼저 보여 준 보관 탭.

- **목록은 시작점이 있는 하나의 목록이다.** 생성할 때 준 `screens`가 시작 목록이다. `register`, `unregister`, `retainOnly`가 살아 있는 목록을 바꾸고, `reset()`은 모든 탭을 닫고 목록을 시작 목록 그대로 되돌린다(등록·수정·제거가 모두 사라진다).
- `register(screen)`는 정의를 추가하거나 고친다. 열린 화면을 고치면 제목과 페이지가 읽는 화면 객체는 바뀌지만 **탭 객체·페이지·데이터는 그대로**다. 탭은 처음 만들 때의 컴포넌트를 계속 그린다. 새 `component`는 `renew`로만 적용되고 저절로 바뀌지 않으므로, 수정이 페이지를 다시 만드는 일은 없다. `{ show: true }`를 주면 `beforeActivate` 없이 그 화면을 활성으로도 만든다. 라우터가 이미 허락했기 때문이다. `{ renew: true }`를 주면 열린 탭을 그 자리에서 바꾼다(같은 slot, 같은 위치, 새 인스턴스, 새 데이터). 이때 옛 페이지는 버려진다. fm 기사 화면이 허용된 페이지를 "메뉴 거부" 페이지로 바꿀 때 필요하다.
- `show(id)`는 이미 등록된 id에 대해 라우터가 "이제 이 화면이다"라고 알리는 것이다. 가드를 부르지 않는다.
  - **지금 확인 중인 화면을 보여 주는 것은 그 확인의 일부다.** fm에서 모든 확인은 "라우터 이동"이고, 확인이 끝나기 전에 route가 바로 그 화면에 대해 `register(page, { show: true })`를 부른다. 이 show는 확인을 끝내지도 앞지르지도 않는다. 확인은 여전히 가드 자신의 답으로 끝난다.
  - **다른 화면을 보여 주면 진행 중인 확인을 앞지른다.** 그 확인은 `stale`이 된다. 0.2.0에서 뒤이은 `open`이나 `select`가 그런 것과 똑같다.
- **확인이 거절되면, 확인하던 화면이 보이고 있을 때만 화면을 비운다.** 거절되는 순간 확인하던 화면이 활성이면(먼저 보여 준 보관 탭, 닫힌 탭의 이웃, 라우터가 이미 보여 준 새 화면) 결과는 `denied`이고 활성 화면이 없다. 보이지 않고 있었다면(아직 아무것도 보여 주지 않은 평범한 `open()`) 지금처럼 아무것도 바뀌지 않는다. 가드가 예외를 던지면 거절처럼 처리하고 그 오류를 넘긴다(0.2.0과 같음).
- 아직 등록되지 않은 id를 `open(id)`할 때: `beforeActivate`가 없으면 지금처럼 바로 `unknown`. 가드가 있으면 먼저 탭 개수 제한(새 탭으로 셈)을 보고, 가드를 부르고(fm의 가드는 "라우터 이동"), 목록은 가드 **뒤에** 본다. 그사이 route가 화면을 등록했으면 열리고, 아니면 `unknown`.
- `showRetainedFirst: true`: 이미 열린 탭을 `open(id)`하면 바로 활성으로 만들고 나중에 확인한다. 0.2.0이 닫힌 탭의 이웃을 보여 주는 방식과 같다.
- `unregister`, `retainOnly`, `reset`은 **닫기가 아니라 회수**다. 탭만이 아니라 정의도 없애므로, 이후 `open(id)`는 다시 가드에게 묻는다(권한이 돌아왔는지는 라우터가 정한다). `beforeClose`는 부르지 않고(권한이 없어졌는데 "저장 안 한 내용" 확인은 의미가 없다), 이웃도 보여 주지 않는다. 활성 탭이 제거되면 앱이나 라우터가 다른 화면을 보여 줄 때까지 활성 화면이 없다. 제거된 화면에 대해 진행 중이던 확인·열기·닫기는 `stale`로 끝나고, 나머지 요청은 계속된다.
- `home`: 홈 화면 탭 하나만 남았을 때 닫으면 거절(`cancelled`)이고, `canClose`가 false를 알려 파츠가 그 버튼을 끈다. 다른 화면의 마지막 탭을 닫으면 바로 없애고 홈을 가드를 거쳐 연다. `close`는 그 열기의 결과로 끝난다. 다른 탭이 남아 있으면 홈은 관여하지 않는다.
- `pendingId`는 종류와 상관없이 확인이 진행 중인 id다. 그래서 닫기 뒤 이웃이나 홈을 확인하는 동안에도 바쁨 표시가 보인다. 파츠는 보관 탭에 바쁨 표시를 하고, 아직 등록되지 않은 id의 자리표시 탭은 선택해서 쓰는 슬롯으로 둔다. 제목은 앱만 알기 때문이다(fm은 메뉴에서 가져온다).
- **화면은 컨트롤러를 통해 넣는다.** 컴포넌트 prop을 바꾸는 방식이 아니다. 워크스페이스 안에서는 `useWorkspace().register(...)`, 아니면 바깥에서 만든 컨트롤러를 넘긴다. `screens` prop은 지금처럼 한 번 읽는 시작 목록으로 남는다. SSR 재현이 단순해진다.
- **페이지는 자기 탭을 읽는다.** 네 어댑터 모두 `useWorkspacePage()`에 `data`(탭의 데이터)와 `screen`(현재 정의, 다시 등록하면 따라 바뀜)을 더한다. 패키지 기본 패널은 지금처럼 props 없이 컴포넌트를 그린다. props가 필요한 앱은 거기서 읽거나, fm처럼 `RetainedPanels`로 직접 그린다.
- **리스너는 스냅샷 변화에 반응해서 화면을 등록하거나 보여 주면 안 된다.** 구독자와 `onChange`는 매 반영 안에서 동기로 실행되고, 다음 확인보다 먼저 돈다. 등록은 나중에 움직이는 앱의 라우터 몫이다.

**fm이 쓰는 방법.** `WorkspaceRoute`는 그대로 두고, 그 `register()`가 이렇게 된다. 식별이 바뀌었으면 `reset()` → `retainOnly(허용 목록 + 이 경로)` → `register(page, { show: true, renew: 기사화면교체 })` → `limit`이면 지금과 같은 토스트와 되돌아가기. `beforeActivate`는 "라우터를 이 경로로 이동하고, 그 경로가 성공했는지 알려 주기"다. fm은 페이지를 계속 `RetainedPanels`로 그리되 `snapshot.tabs`를 넣고, DDS 탭 줄·전환기 대화상자·단축키는 자기 것을 유지한다.

**어댑터.** 네 개 모두: "컨트롤러와 컴포넌트의 화면 목록이 같아야 한다"와 "메뉴가 모르는 화면을 가리킨다" 검사를 없앤다(`Workspace.tsx:65-66`, `react.tsx:37`, `vue.ts:37-38`, `WorkspaceProvider.svelte:12-13`). 컨트롤러가 컴포넌트를 가진 화면을 담는 유일한 목록이 된다. 제목이 따라 바뀌도록 화면은 스냅샷에서 찾고, DOM id는 slot으로 만들고, `canClose`가 false면 닫기 버튼을 끄고, 바쁨 상태를 그린다. 메뉴 항목은 아직 등록되지 않은 화면을 가리켜도 되며, 그런 항목은 자기 라벨을 가져야 한다. Vue는 setup에서 스냅샷을 읽지만 구독은 마운트 뒤에야 시작해서(`vue.ts:39-40`), 서버에서는 provider setup 이후의 등록을 놓친다. Svelte 어댑터처럼 setup에서 구독해야 한다.

**SSR.** 코어는 동기로 남는다. 네 어댑터 공통 규칙: 요청별 컨트롤러에 렌더 **전에** 화면을 등록하고 보여 주고, 클라이언트에서 같은 등록을 같은 순서로 다시 해서 하이드레이션 때 slot이 맞게 한다. Solid와 Svelte는 탭 파츠보다 먼저 일어나기만 하면 렌더 중 등록도 견딘다(지금 fm이 하는 방식). React는 렌더 중 부작용을 허용하지 않으므로 "렌더 전"만 지원한다.

**0.2.0 닫기 계약.** 사용자가 닫는 경우는 그대로다. 회수는 `reset()`처럼 닫기와 별개로 정의한다. 0.2.0 문장 "뒤이은 `open`이나 `select`가 반영되면"에 "또는 `show()`가 다른 화면을 활성으로 만들면"이 붙는다. `show()`를 부르지 않는 앱에는 바뀌는 게 없다. fm이 기대는 순서 하나를 적어 둔다. 닫기가 반영되고, 리스너에게 동기로 알리고, 이어서 같은 동기 흐름 안에서 이웃(또는 홈)의 `beforeActivate`를 시작한다. 그 사이에 기다리는 것이 없다. 그래서 라우터 연결은 기다려야 하는 작업(로더, 새로고침)이 돌기 전에 위치를 옮기고, 닫힌 화면이 스스로 다시 등록될 수 없다. 먼저 도는 것은 리스너 코드뿐이고, 그래서 리스너가 화면을 등록하면 안 된다.

**URL 어댑터.** `createHistoryWorkspace`는 하던 일(패키지가 URL을 소유)을 그대로 하고 새 제네릭 옵션만 받아들인다. 등록되지 않은 id로 뒤로/앞으로 가면 이제 가드를 부르고(목록은 가드 뒤에 본다), `dispose()`는 목록을 시작 목록으로 되돌린다. fm처럼 자기 라우터가 URL을 소유하는 앱은 `show()`를 쓰고 `createHistoryWorkspace`와 함께 쓰지 않는다. URL 주인이 둘인 경우는 지원하지 않는다.

**버전.** 0.3.0, 깨지는 것: 가드가 있을 때 `open()`이 등록 안 된 id에도 가드를 부른다(`createHistoryWorkspace`의 뒤로/앞으로에도 해당). 전환기의 DOM id가 화면 id 대신 slot으로 바뀐다. `reset()`과 history 어댑터의 `dispose()`가 실행 중 등록을 버린다. 나머지는 모두 추가뿐이다.

- **장점:** 상태 기계가 하나이고, 한 번 테스트해서 fm과 다른 사용자가 같이 쓴다. fm이 손으로 고쳐 온 순서 규칙(닫기 순서, stale, 개수 제한, 보관 탭 먼저 보여 주기)이 패키지 테스트에 들어간다. 고정 목록 앱은 지금처럼 `screens`를 넘기면 그대로 동작한다.
- **단점:** 세 안 중 가장 큰 변경(코어와 어댑터 네 개). 코어 API에 메서드 일곱 개와 옵션 세 개가 늘어난다. `show()`와 `register({ show })`는 일부러 가드를 건너뛰므로, 앱의 라우터용이라고 문서에 분명히 적어야 한다.

### B안 — 목록은 앱이, 파츠는 패키지가 (코어 변경 없음)

`RetainedPanels` 방식을 탭 줄, 전환기, 단축키까지 넓힌다. 앱이 가진 `items` 목록과 `activeId`, `onSelect`, `onClose`, `title`, `slot` 콜백을 받는 새 파츠를 만든다. 패키지는 그리기와 키보드를 맡고, 상태는 모두 앱이 갖는다.

- **fm이 지우는 것**은 탭 줄 마크업, 전환기 방향키 처리, 단축키 설정 정도(약 50줄)이고, 상태 기계는 전부 남는다.
- **어댑터:** 네 개 각각에 새 파츠 두세 개. 코어는 그대로.
- **SSR:** 앱이 이미 가진 것을 그리므로 가장 쉽다.
- **0.2.0 닫기 계약:** 이런 앱에서는 패키지가 더 이상 지켜 주지 않는다. 앱마다 닫기 순서를 다시 구현한다(fm은 #151부터 이미 그렇게 한다).
- **버전:** 0.3.0, 추가만 있고 깨지는 것 없음.
- **장점:** 가장 작고 안전한 변경, 기존 사용자가 옮길 것이 없다.
- **단점:** 합의한 일을 하지 않는다. 2026-10-20에 두 번 고치게 만든 중복 규칙이 그대로 남고, 앞으로도 탭 순서 수정은 매번 두 번 써야 한다.

### C안 — 화면을 물어보는 함수 (패키지가 물어봄)

앱이 화면을 넣어 주는 대신 컨트롤러가 묻는다: `createWorkspace({ resolveScreen(id): S | undefined | Promise<S | undefined> })`. 모르는 id를 `open(id)`하면 가드 뒤에 이 함수를 부르고 답을 기억한다. 회수에는 여전히 `retainOnly`가 필요하다.

- **잘 맞는 곳:** 허용 화면을 서버 목록에서 받는 앱("이 사용자가 열 수 있는 화면은?").
- **fm만으로는 안 맞는다:** fm 화면은 링크, 뒤로/앞으로, 직접 입력 URL로도 나타나는데, 이때는 `open()`을 부르지 않으니 아무도 이 함수에 묻지 않는다. fm에는 결국 A안의 넣어 주는 메서드(`register`, `show`)가 필요하다.
- **SSR:** 비동기 함수는 렌더 중에 돌 수 없으므로 A안의 "렌더 전" 규칙으로 돌아간다.
- **버전:** 0.3.0, 대부분 추가.
- **장점:** 권한 목록형 앱에 깔끔하다.
- **단점:** fm에게는 A안에 개념 하나가 더 붙는 것. 실제로 원하는 소비자가 생기면 나중에 A안 위에 더할 수 있다.

## 5. 추천

**A안**을 0.3.0으로 내고, fm은 별도 PR에서 **코어만** 받아들인다. DDS 탭 줄, 전환기 대화상자, 단축키, `RetainedPanels`는 fm 것을 유지한다. fm이 나중에 패키지의 전환기·단축키 파츠까지 쓸지는 따로, 나중에 정한다.

권하는 순서(만드는 사람이 단계를 합쳐도 된다): 코어 규칙과 테스트 → 네 어댑터, 문서, CHANGELOG → 0.3.0 출시 → fm 자체 출시 규칙에 따른 fm 적용 PR.

**첫 계획이 끝나는 곳.** 패키지 계획은 검증된 0.3.0 PR이 머지되는 데서 끝난다. 그 PR이 머지되면 0.3.0을 패키지 출시 워크플로로 npm에 낸다(`docs/releasing.md`). 소유자가 2026-10-20에 미리 허락했으므로 다시 묻지 않는다. fm 적용은 별도의 나중 계획이다. fm `AGENTS.md`가 지금 테스트·lint·build·typecheck 실행을 금지하고 머지를 제한하므로, fm 규칙이 검증을 허락할 때에야 계획할 수 있다.

## 7. 이 설계에서 내린 판단 (아직 소유자 합의 전)

검토자가 초안을 만드는 사람 입장에서 읽으며 나온 것들이다. 작성자의 판단이며 소유자가 어느 것이든 뒤집을 수 있다.

1. 확인 중인 화면의 `show()`는 그 확인의 일부이고, 여전히 가드의 답이 결정한다. 다른 화면의 `show()`는 확인을 앞지른다(`stale`).
2. 확인이 거절되면, 확인하던 화면이 보이고 있을 때만 화면을 비운다. 아니면 아무것도 바꾸지 않는다.
3. 회수는 정의까지 없애고, `reset()`은 시작 목록 그대로 돌아간다.
4. 다시 등록된 화면도 탭이 만들어질 때의 컴포넌트를 유지한다. 바꾸는 건 `renew`뿐이다.
5. `pendingId`는 닫기 뒤 이웃과 홈을 포함한 모든 확인을 덮는다.
6. 화면은 컨트롤러로 넣고, `screens` prop은 한 번 읽는 시작 목록으로 남는다.
7. `useWorkspacePage()`에 `data`와 `screen`이 생기고, 패키지 기본 패널은 여전히 props를 넘기지 않는다.
8. `home`과 `showRetainedFirst`는 패키지에 둔다(fm에 둘 다 필요하고, 둘 다 순서 문제라 패키지 몫이다). 둘 다 설정하지 않으면 꺼져 있다.
9. `createHistoryWorkspace`와 `show()`는 함께 쓰지 않는다. 워크스페이스마다 URL 주인은 하나.

## 8. 만드는 사람에게 맡기는 것

- 내부 방식(진행 중인 확인을 어떻게 추적할지, `register({ show })`와 `retainOnly`가 같은 흐름에서 한 번 알릴지 두 번 알릴지). 두 반영 사이에 화면이 깜빡이는 게 테스트에서 보이면 작은 `transaction(fn)` 도우미를 둬도 된다.
- 타입 매개변수 이름과 기본 타입 인자.
- 자리표시 슬롯을 어댑터마다 하나 둘지, `tabLabel`을 재사용할지.
- 테스트 파일 구성. 단, 4장 A안의 규칙마다 코어 테스트가 있고, 어댑터에는 동등성 검사, 미리 연 요청별 컨트롤러로 하는 SSR 검사, 경로 모양 id의 끝단 검사가 있어야 한다.
